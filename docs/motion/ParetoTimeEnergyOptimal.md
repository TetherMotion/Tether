# SnapSpace Time–Energy Profile Planning

**Manual for `ParetoTimeEnergyOptimalVelocityPlanner`**

## Status and contract

`ParetoTimeEnergyOptimalVelocityPlanner` produces a fourth-order, snap-limited
path trajectory.  The historic implementation mixed a third-order `a*` search,
post-propagation state clamps, and a separate forward-pass state machine.  That
is not a valid optimal-control implementation because the costed, stored, and
sampled trajectories can differ.

The current implementation has one deterministic, exact pulse kernel. It is a
**feasible-family optimiser**, not a proof of the globally Pareto-optimal
solution for arbitrary varying constraint walls. It searches a finite,
reproducible family of globally conservative trajectories and selects the
minimum exact weighted cost. Do not present it as a global Pontryagin solution
without replacing this restricted-family search with a certified optimisation
method.

The public boundary contract is

$$
(s,v,a,j)(0)=(0,v_0,0,0),\qquad
(s,v,a,j)(T)=(L,v_f,0,0).
$$

The current `VelocityProfiler` endpoint API cannot express final acceleration
or jerk. A request with nonzero initial acceleration or jerk is therefore
rejected rather than silently resetting either state.

## Dynamics and cost

The path coordinate is $s$, with path velocity $v$, tangential acceleration
$a$, jerk $j$, and snap $\sigma$:

$$
\dot{s}=v,\qquad \dot{v}=a,\qquad \dot{a}=j,\qquad \dot{j}=\sigma.
$$

The cost used to compare candidates is evaluated exactly over every arc:

$$
J=\int_0^T\left(w_t+w_jj(t)^2+w_aa(t)^2\right)dt.
$$

`w_t` must be positive. `w_j` and `w_a` may be zero. The selected solution is
the lowest-cost feasible member of the candidate family, not an approximation
of a different cost functional.

## Trajectory construction

1. `ConstraintEvaluator` samples the path to obtain a conservative path-wide
   velocity envelope and symmetric tangential acceleration/jerk authority.
2. The solver generates symmetric acceleration and braking pulses from exact
   SNAP and SINGULAR arcs. Pulses may be triangular, jerk-plateau, or
   acceleration-plateau shaped.
3. A bounded bisection finds the greatest reachable peak velocity for the
   requested endpoint speeds and path length. Remaining distance is a
   zero-jerk cruise arc.
4. Forty-one deterministic limit scales from $1$ to $0.01$ are evaluated. The
   candidate with the minimum finite closed-form cost is selected.

This path-wide envelope deliberately sacrifices speed where limits vary over a
path. That is conservative and coherent; it does not claim to track a local
velocity wall. A future global optimiser must maintain viable $(v,a,j)$ sets
through every local constraint boundary and prove terminal reachability.

## Constraints

The solver requires strictly positive numeric path limits for acceleration,
jerk, and snap. Its own fourth-order dynamics enforce these values even when
legacy `jerkLimitEnabled` flags are disabled for lower-order profilers.

Velocity, acceleration, and jerk authority are derived from the supplied path
and its axis/path limits. The bounds are sampled conservatively before a pulse
is constructed. A generated arc is never post-clamped during sampling.

Per-axis snap limits are intentionally rejected. Correct conversion of
Cartesian axis snap constraints needs fourth arc-length geometry derivatives:

$$
q^{(4)} = p^{(4)}v^4 + 6p^{(3)}v^2a + 3p''a^2 + 4p''vj + p'\sigma.
$$

The current geometry interface provides derivatives only through order three.
Returning a profile under enabled axis snap limits would therefore imply a
certificate that the implementation cannot provide. The failure reason is
`Per-axis snap limits require fourth-order path derivatives`.

## Weighted switching structure

The selected trajectory is stored in a `WeightedSwitchingStructure` (WSS). It
is the source of truth for sampling, inversion, and cost. Each `WeightedArc`
stores

- its type and absolute time/arc-length interval;
- initial state `v0`, `a0`, `j0`;
- control (`sigma` for SNAP, `j_star` for SINGULAR);
- exact terminal state `v1`, `a1`, `j1`;
- an `activeConstraints` bit mask: velocity `1`, acceleration `2`, jerk `4`,
  snap `8`.

The normal solver emits `SNAP_PLUS`, `SNAP_MINUS`, and `SINGULAR` arcs.
`DWELL` is used when the path has dwell points. `WALL` remains readable for
legacy WSS data but is not generated by the current pulse kernel.

For a SNAP arc of duration $\tau$,

$$
\begin{aligned}
j(\tau)&=j_0+\sigma\tau,\\
a(\tau)&=a_0+j_0\tau+\tfrac12\sigma\tau^2,\\
v(\tau)&=v_0+a_0\tau+\tfrac12j_0\tau^2+\tfrac16\sigma\tau^3,\\
s(\tau)&=s_0+v_0\tau+\tfrac12a_0\tau^2+
          \tfrac16j_0\tau^3+\tfrac1{24}\sigma\tau^4.
\end{aligned}
$$

For a SINGULAR arc, $j=j_*$ is constant and the corresponding formulas are
obtained by setting $\sigma=0$.

`startState()` and `endState()` expose the stored exact endpoint states.
`timeAtArcLength()` only bisects over the selected arc's recorded duration,
which prevents it from selecting a later deceleration root. `arcLength()`,
`pathVelocity()`, `pathAcceleration()`, and `pathJerk()` report the stored
trajectory without output-time clamps. A detected violation must be fixed in
the solver, never hidden in a sampling accessor.

## Failure behavior

`computeProfile()` returns an empty sampled profile when a request is invalid
or no candidate is feasible. Call `failureReason()` on the planner for the
cause. Typical reasons are:

- a nonpositive feed or invalid path limit;
- an endpoint velocity outside the conservative path envelope;
- a path too short for the requested velocity transition;
- unsupported nonzero initial $a$ or $j$;
- enabled per-axis snap limits.

## Related profilers

- `AnalyticalTOPPRA`: explicit second-order, no-jerk-limit profile. It reports
  meaningful velocity and acceleration only.
- `AnalyticalJerkLimitedTOPPRA`: third-order jerk-limited analytical/SSR
  profile. It requires a positive enabled jerk limit.
- `JerkConstrainedTOPPRA`: sampled third-order TOPP-RA approximation.
- `SCurveVelocityProfiler`: per-piece jerk-limited S-curve profile.

Use `VelocityProfile::derivativeOrder()`, `hasJerk()`, and `hasSnap()` before
using optional derivative fields. A zero stored in a lower-order sampled
profile's `jerk` field is compatibility storage, not a physical zero jerk.

## Verification

`SnapSpaceContractTest.cpp` independently checks SNAP/SINGULAR propagation and
inversion, WSS endpoint state, arc continuity, monotone mappings, curve
velocity envelopes, constraints, exact closed-form cost versus quadrature,
axis-snap rejection, profiler selection, and repeated-coordinate sampling.
The integration tests additionally exercise profiler construction, existing
G-code paths, and analytical extrusion consumers.
